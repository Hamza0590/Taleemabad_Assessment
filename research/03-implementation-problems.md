# Research 03 — Problems waiting for us in the prototype
Date: 2026-11-25. Each problem: what it is, options, and Claude's recommendation. Decisions go to D-008+.

## P1. Data: we have no real board scripts
Boards won't give us real student scripts (privacy, secrecy rules).
Options:
 a) Create our own: print real past-paper questions, have several people (friends, hostel mates)
    handwrite answers, then mark them like an examiner with a red pen (ticks + marks).
 b) Public handwriting datasets (e.g. IAM, English). They're NOT exam answers, and have no ticks or marks.
 c) Fully synthetic images (rendered handwriting fonts). Fast, but unrealistic.
Recommendation: (a), small but real, with (c) only to stress-test if time allows.

## P2. Ground truth: what is the "correct" mark?
Physics long answers have some subjectivity; even two honest examiners differ by a mark or two.
Options: use a tolerance (e.g. ±1 mark per question isn't an error); define error types clearly.
Recommendation: define planted error types objectively:
  E1 ticked-but-marked-down, E2 unmarked question, E3 wrong total, E4 marks over maximum,
  E5 under-credited correct answer (no tick issue, just low marks), E6 over-credited wrong answer.
  E1–E4 are objective. E5–E6 need the tolerance rule.

## P3. Circularity: we plant the errors AND build the detector
If we know where the errors are, we might (even unconsciously) design the detector to find them.
Options: someone else plants the errors using a random protocol (a script decides which
scripts/questions get which error), and the answer key stays sealed until evaluation.
Recommendation: a random error-injection plan generated by code before marking; detector
developed without looking at it. Report this limitation honestly anyway.

## P4. Reading the script: handwriting, equations, diagrams, ticks
- Can a VLM read handwritten physics (formulas, units, diagrams)? Unknown. Experiment 1.
- Separating examiner marks from the student's writing: examiners use red ink, students use
  blue/black. Colour segmentation could isolate ticks and marks. Simple and explainable.
- Image quality: phone photos vs flatbed scans (shadows, tilt). Boards would scan; we'll likely use phones.
- Which answer belongs to which question: traditional answer books are free-form; FBISE e-sheets
  have fixed boxes per question. Recommendation: use a fixed-box answer sheet (like e-sheets)
  so layout is solved and we focus on the real question.

## P5. The marking scheme
The AI second reader needs a rubric (key points + marks per step). Punjab boards don't publish
detailed marking schemes (to verify). Recommendation: write a rubric per question ourselves,
the way a head examiner would, and say so.

## P6. Language
Many students write in Urdu medium. Urdu handwriting OCR is much weaker. Recommendation: scope
v1 to English-medium FSc Physics (the user's own subject and story). State Urdu as future work.

## P7. False flags and trust
If many flags are false, reviewers waste their 20% budget and stop trusting the tool.
H1's fixed-budget design measures exactly this, which is good.

## P8. Compute and scale
~20M scripts/year means per-script inference time matters (feeds H2). Need to measure seconds
per script on a local GPU with an open-weight VLM. Choose a model that fits available VRAM.

## P9. External validity
Our planted errors may be easier or harder than real examiner errors, and the real error
distribution is unknown (no board publishes it). Must be stated as the main limitation.

## P10. Time: 2 days
Everything must fit. Smallest version that still tests H1:
 ~1 question paper, ~6–10 questions, ~20–40 handwritten scripts, a few writers,
 errors planted by script, consistency audit + VLM second reader, random vs ranked comparison.

## P11. Fairness of the AI itself
The AI may score messy handwriting lower, so it ranks those scripts as "examiner over-marked"
or misses under-marking there. Check performance by writer if data allows. Future work otherwise.
